# El artefacto de restricciones · lo que `generated/contract/` tiene que traer además

**Carpeta**: `006-el-merchant-completo` · **Fecha**: 2026-10-08 · Completa a
[`../../005-la-base-de-ope/contracts/contract-artifact.md`](../../005-la-base-de-ope/contracts/contract-artifact.md)

**A quién le habla**: a OPE-Backend, para su feature 040; y a `scripts/contract-sync.mjs`, que lo
emite mientras tanto con la misma forma. Cuando el backend lo emita, el sincronizador copia en vez de
emitir, igual que con el módulo de capacidades.

## Qué es

**La capa 1 de `CU-38`**: lo que un formulario puede verificar localmente y gratis, sacado de
`components.schemas` del bundle. No incluye `x-invariants` (capa 2 y 3): una regla en prosa no se
emite como predicado.

## Los archivos

### `constraints.js`

```js
// GENERATED by <emisor> — DO NOT EDIT BY HAND.
export const CONTRACT = { version: '1.11.0', sha256: '…' }   // la misma identidad que capabilities.js

export const CONSTRAINTS = {
  MerchantCreate: {
    required: ['origins', 'signature'],
    fields: {
      origins: { type: 'array', minItems: 1, maxItems: 20, items: { type: 'string', maxLength: 255 } },
      signature: { type: 'boolean' },
    },
  },
  CredentialRotation: {
    required: [],
    fields: { graceSeconds: { type: 'integer', minimum: 0 } },
  },
  KillSwitch: {
    required: ['enabled'],
    fields: { enabled: { type: 'boolean' } },
  },
  // …
}
```

### `constraints.d.ts`

Declara `FieldConstraints`, `MessageConstraints` (con la forma de `packages/core/src/ui/use-form.ts`,
que gana `minItems`, `maxItems` e `items`) y `CONSTRAINTS` con **una clave por esquema**, tipada
como `MessageConstraints`, para que `CONSTRAINTS.MerchantCreate` compile y `CONSTRAINTS.MerchantCreat`
no.

## Qué esquemas entran

Todo `components.schemas.<Name>` con `type: object` que algún `requestBody` de un consumidor
referencie, **directa o transitivamente** (un objeto anidado entra con su propio nombre, y la
propiedad que lo referencia lleva `{ type: 'object', ref: '<Name>' }`). Los esquemas de respuesta no
entran: nadie los teclea.

## Qué se lee de cada propiedad

| JSON Schema | campo emitido |
|---|---|
| `type` (si es uno solo) | `type` |
| `minLength`, `maxLength`, `pattern` | tal cual |
| `minimum`, `maximum` | tal cual (`exclusiveMinimum`/`Maximum` no se emiten: no hay formulario que los use todavía; se anota) |
| `minItems`, `maxItems`, `items` (recursivo) | tal cual |
| `$ref` a otro esquema objeto | `{ type: 'object', ref: '<Name>' }` |
| `enum` | `enum: [...]` |
| `format` | `format` |
| `default` | no se emite: la omisión es del servidor, no del formulario |
| `description` | no se emite: el rótulo es de la aplicación (`CU-43`) |

`required` es el del esquema; ausente, `[]`.

## Cómo se verifica

`ope-check conformity` carga `constraints.js` y, contra el bundle:

- `CONTRACT` coincide con `identity.json` (misma identidad que el módulo de capacidades).
- Cada clave de `CONSTRAINTS` existe en `components.schemas` y es `type: object`.
- `required` de cada entrada es igual al del esquema.
- Cada esquema objeto referenciado por un `requestBody` está en `CONSTRAINTS`.
- Informa cuántos revisó; **falla con cero**.

## Lo que NO es

- No reemplaza a `api.d.ts`: los tipos siguen saliendo de `openapi-typescript`. Esto es lo que los
  tipos no dicen (un `maxLength` no es un tipo).
- No decide qué campo es obligatorio **en la pantalla**: una aplicación puede pedir menos campos de
  los que el servidor exige si los completa sola. `required` es lo que el servidor exige.
